## Exact privilege and function review

The live catalog currently contains only the existing library and source workout tables for this scope. Their four RLS policies are:

- `read published exercises`: SELECT for anon/authenticated with `is_published`; no catalog write policy.
- `users manage own workout plans`: ALL for authenticated, `user_id = auth.uid()` in both USING and WITH CHECK.
- `users access own workout days`: ALL for authenticated, owned parent plan in both predicates.
- `users access own workout exercises`: ALL for authenticated, owned parent day/plan in both predicates.

Existing public table ACLs/default ACLs grant broad privileges to anon/authenticated, including TRUNCATE. RLS gates row access but does **not** gate TRUNCATE. This is a pre-existing privilege-hardening concern, not a demonstrated REST truncate exploit: anon/authenticated have no LOGIN and public schema CREATE is denied. The new save routine has no dynamic SQL or arbitrary statement execution path. The proposal explicitly revokes all client/PUBLIC privileges on its three new tables, then grants only authenticated SELECT. The local test now recreates broad public default grants to verify that revocation remains effective.

For the proposed objects, owner SELECT RLS restricts parents to `(select auth.uid())`; child reads follow the parent owner's identity and do not depend on nullable historical source links. Writes run only through a validated routine. The public wrapper is SECURITY INVOKER and calls the schema-qualified private implementation. The private definer and wrapper both set `search_path = ''`. Anonymous/PUBLIC EXECUTE is revoked; authenticated EXECUTE is deliberate on both routines. Authenticated private-schema USAGE permits delegation, not CREATE. The trigger function is not client-executable.

Calling the private routine directly does not bypass authorization: it checks `auth.uid()`, payload owner, existing session owner, active owned source relationship and approved/enabled mappings at registration. Its source/actual primary-target checks are now null-safe. Registered updates require an unchanged immutable envelope; they update flags, not another prescription or user. Direct writes to session/set/mapping tables are denied. The owner/service role remains privileged administration; this is not a guarantee against a compromised administrative credential.

Current PostgREST exposed-schema configuration could not be established from database settings (`pgrst.db_schemas` was unset in the inspected settings). **Confirm in hosted/staging Data API settings that `public` is exposed and `arc_private` is not**, then verify actual REST wrapper permissions/cache visibility after deployment. This is a release prerequisite, not a claim already tested.

Two pre-existing public SECURITY DEFINER routines, `handle_new_user()` and `rls_auto_enable()`, are executable by anon/authenticated. Their configured search paths are `public` and `pg_catalog`, respectively. They are outside this migration; exposure alone is not proof that a trigger/event-trigger function is a working arbitrary RPC. Their advisor findings need separate owner review. Existing `meal_nutrition` definer-view, mutable `set_updated_at` search path, public vector extension, knowledge-table policy and Auth password-protection notices remain unchanged. See the audit and official remediation guidance for [definer function exposure](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [definer views](https://supabase.com/docs/guides/database/database-linter?lint=0010_security_definer_view), and [search paths](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable).

## State, history and mapping semantics

- New sessions validate the current active owned plan/day and original snapshot. Gym remains its saved prescription. Home must use exact approved/enabled mapping IDs and versions, real published actual IDs, compatible capabilities, curated volume and recalculated duration.
- A transaction/advisory lock serializes same-user/day registration. Stable UUIDs and a unique in-progress index prevent duplicate first inserts. Concurrent identical first-insert retries passed on the packaged migration.
- Same-revision retries require matching flags, status, outcome, end timestamp and index. Higher revisions require the exact current base revision. Finished sessions accept identical retries but cannot reopen, change outcome or accept further progress changes.
- Completed requires all checked sets; partial cannot claim all sets complete; discard preserves whatever flags were actually checked. Timestamp ordering and future bounds are validated; existing deliberate historical/backdated starts are not newly forbidden.
- Source plan/day/set-source/actual/mapping relational links use SET NULL for historical retention. Immutable JSON retains original identities. Mapping source/alternative catalog FKs themselves use RESTRICT: deleting a referenced catalog row first requires the appropriate controlled mapping/source cleanup. The tests perform such cleanup only in the disposable fixture.
- Approval initially permits editing the proposed definition and recording review metadata in the same controlled approval update. Thereafter definition/version/metadata are frozen. Disabling/retiring is permitted. Re-enabling/re-approving an unchanged retired definition is also permitted by the current trigger; retirement is not a terminal status. There is no claim that this constitutes professional or medical clearance.
- The seed's `ON CONFLICT (id) DO NOTHING` makes repeat insertion non-overwriting. On a fresh schema the six rows remain proposed/disabled. It does not forcibly downgrade an existing administrator-approved row; unexpected existing IDs must be reviewed before seeding.

## Rollback considerations

Before commit, PostgreSQL rollback removes that file's changes. After commit, prefer a forward corrective migration and preserve recorded user history. Disable/retire problematic mappings to block new adaptations while leaving existing authorized snapshots intact. To pause saves, a separately reviewed administrative change can revoke authenticated EXECUTE on **both** public and private save functions, retaining tables and owner-read history; the app must then retain local drafts and show unconfirmed saves.

Do not use blanket `DROP ... CASCADE`, drop `arc_private` wholesale, delete user sessions or rerun the prototype schema as rollback. A full schema removal would destroy workout history and requires an explicit data-preserving plan, backup/restore decision and approval. Remove the added source FK index only if the rollback owns it and no later change depends on it. Preserve seed versions used by history; disable rather than rewrite/delete them. Any migration-history rollback/repair is itself a live write requiring approval.
